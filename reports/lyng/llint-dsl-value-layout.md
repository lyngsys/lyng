# Lyng-js Value layout — DSL substrate prerequisite report

This report documents the current `Value` representation in lyng as the
source of truth for the DSL backend's `check_*!` / `tag_*!` / `untag_*!`
macros. It is the first of three R-0 evidence reports required before
DSL-0 begins (the other two cover the handler ABI and the safepoint /
allocation model). The DSL substrate generates AArch64 / x86_64
assembly from a small set of typed value primitives; those primitives
have to compile to the *exact* bit-test and untag sequences that the
current `Value` encoding implies, not to whatever JSC's `JSCJSValue`
encoding implies, because the two encodings differ in concrete ways
documented below.

## Encoding overview

`Value` is an 8-byte `#[repr(transparent)]` newtype over `u64`
([value.rs:73-75](../../../crates/types/src/value.rs)).
The encoding is a NaN-tag-space scheme: every non-double value is
hidden inside a canonical NaN-prefixed bit pattern; finite doubles
(and NaN) sit in the rest of the IEEE-754 64-bit space.

The 64-bit layout for a tagged (non-double) `Value`, MSB to LSB, is:

```
 63                51                  47                  31                                0
  |                 |                   |                   |                                 |
  0111 1111 1111 1000   kkkk kkkk kkkk kkkk   pppp pppp pppp pppp pppp pppp pppp pppp pppp pppp
  \_________ ____________/  \_________ _________/  \_______________ ______________/
            |                         |                            |
       TAG_HEADER                TAG_KIND_MASK                  PAYLOAD_MASK
   0x7ff8_0000_0000_0000     0x0000_ffff_0000_0000          0x0000_0000_ffff_ffff
            |                         |                            |
       canonical NaN              16-bit kind                32-bit payload
       prefix (top 13              discriminator               (ObjectRef id,
       bits = quiet NaN)           (TagKind enum)              SMI bits, etc.)
```

Constants ([value.rs:4-8](../../../crates/types/src/value.rs)):

| Constant            | Value                  | Role                                                |
| ------------------- | ---------------------- | --------------------------------------------------- |
| `TAG_HEADER`        | `0x7ff8_0000_0000_0000` | Canonical-NaN prefix; set on every non-double `Value`. |
| `TAG_KIND_SHIFT`    | `32`                   | Shift to place the 16-bit kind into bits 32–47.     |
| `TAG_KIND_MASK`     | `0x0000_ffff_0000_0000` | Bits that hold the 16-bit `TagKind` discriminator.  |
| `PAYLOAD_MASK`      | `0x0000_0000_ffff_ffff` | Low 32 bits — the payload (SMI bits, ref id, etc.). |
| `CANONICAL_NAN_BITS`| `0x7ff8_0000_0000_0000` | The single NaN bit pattern doubles canonicalize to. |

A 16-bit `TagKind` enum ([value.rs:11-23](../../../crates/types/src/value.rs))
identifies what the payload means:

| `TagKind`               | Discriminator | Payload                                  |
| ----------------------- | ------------: | ---------------------------------------- |
| `Undefined`             | `1`           | always `0`                               |
| `Null`                  | `2`           | always `0`                               |
| `Boolean`               | `3`           | `0` (false) or `1` (true)                |
| `Smi`                   | `4`           | 32-bit signed integer, raw bits          |
| `ObjectRef`             | `5`           | `NonZeroU32` ObjectRef id                |
| `StringRef`             | `6`           | `NonZeroU32` StringRef id                |
| `SymbolRef`             | `7`           | `NonZeroU32` SymbolRef id                |
| `BigIntRef`             | `8`           | `NonZeroU32` BigIntRef id                |
| `Sentinel`              | `9`           | `InternalSentinel` raw (1–4)             |
| `SuspendedExecutionRef` | `10`          | `NonZeroU32` SuspendedExecutionRef id    |

The tagging core is one helper ([value.rs:78-81](../../../crates/types/src/value.rs)):

```rust
const fn tagged(kind: TagKind, payload: u32) -> Self {
    Self(TAG_HEADER | ((kind as u64) << TAG_KIND_SHIFT) | payload as u64)
}
```

A value is "tagged" (i.e. not a regular double) when its high bits
exactly match `TAG_HEADER` *and* its kind field decodes to a known
`TagKind` ([value.rs:84-86](../../../crates/types/src/value.rs)).
Doubles fall through to the IEEE-754 representation. NaN inputs to
`Value::from_f64` are canonicalized to `CANONICAL_NAN_BITS` so they
cannot collide with a tag-bearing pattern
([value.rs:142-148](../../../crates/types/src/value.rs)).
Test [`finite_doubles_with_tag_kind_bits_are_not_tagged`](../../../crates/types/src/value.rs)
([value.rs:438-465](../../../crates/types/src/value.rs))
proves that finite doubles whose bit pattern overlaps the kind range
still classify as `is_double` and not as any tagged kind — the
`TAG_HEADER` prefix check is what disambiguates.

## Bit masks and predicate semantics

The current encoding intentionally does *not* expose JSC-style
single-mask predicates like `NotCellMask`. Predicates are computed by
exact equality of the high 13 bits to `TAG_HEADER` followed by an
equality check of the 16-bit `TagKind` field.

| Predicate                | Source                                                                                                              | Test performed                                                  |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| `is_tagged_bits(bits)`   | [value.rs:84-86](../../../crates/types/src/value.rs)                                                        | `(bits & TAG_HEADER) == TAG_HEADER` *and* kind ∈ 1..=10        |
| `is_undefined`           | [value.rs:201-203](../../../crates/types/src/value.rs)                                                      | tag-kind == 1                                                   |
| `is_null`                | [value.rs:205-208](../../../crates/types/src/value.rs)                                                      | tag-kind == 2                                                   |
| `is_bool`                | [value.rs:210-213](../../../crates/types/src/value.rs)                                                      | tag-kind == 3                                                   |
| `is_smi`                 | [value.rs:215-218](../../../crates/types/src/value.rs)                                                      | tag-kind == 4                                                   |
| `is_double`              | [value.rs:220-223](../../../crates/types/src/value.rs)                                                      | NOT `is_tagged_bits`                                            |
| `is_number`              | [value.rs:225-228](../../../crates/types/src/value.rs)                                                      | `is_smi() \|\| is_double()`                                     |
| `is_object`              | [value.rs:230-233](../../../crates/types/src/value.rs)                                                      | tag-kind == 5                                                   |
| `is_string`              | [value.rs:235-238](../../../crates/types/src/value.rs)                                                      | tag-kind == 6                                                   |
| `is_symbol`              | [value.rs:240-243](../../../crates/types/src/value.rs)                                                      | tag-kind == 7                                                   |
| `is_bigint`              | [value.rs:245-248](../../../crates/types/src/value.rs)                                                      | tag-kind == 8                                                   |
| `is_sentinel`            | [value.rs:250-253](../../../crates/types/src/value.rs)                                                      | tag-kind == 9                                                   |

The "value is tagged with kind K" predicate factors as
`has_tag(K)` ([value.rs:108-113](../../../crates/types/src/value.rs)),
which structurally is:

```rust
((bits & TAG_HEADER) == TAG_HEADER)
    && ((bits & TAG_KIND_MASK) >> 32) == K as u16
```

The two AND-and-compare operations are what every `check_*!` macro
must compile to.

### Contrast vs JSC `JSCJSValue.h`

JSC uses a *very* different mask family
(`Source/JavaScriptCore/runtime/JSCJSValue.h`):

- `NumberTag = 0xfffe_0000_0000_0000` — set on Int32 (all bits set
  in the top 15) and on doubles (any but not all set after an additive
  encode offset).
- `OtherTag = 0x2` and `NotCellMask = NumberTag | OtherTag` — a cell
  test is `!(bits & NotCellMask)`, i.e. *single* AND-test-zero.
- Booleans/null/undefined live in the low byte as `0x06 / 0x07 / 0x0a / 0x02`.
- `Int32` is encoded as `NumberTag | (uint32_t)i` — payload also in
  the low 32 bits, but the *tag* is in the *high* bits, not in a
  separate kind field.
- Doubles use an additive `DoubleEncodeOffset = 1ULL << 49` so finite
  doubles never overlap the `OtherTag`-based pointer/immediate region.

The deltas that matter for DSL codegen:

1. **`check_cell` cost.** JSC: 1 AND + 1 CBZ. Lyng-js: 1 AND-immediate
   + 1 CMP + 1 B.NE, then a second AND-immediate + CMP + B.NE for the
   kind. The current encoding uses the *quiet-NaN canonical prefix* as
   the tag header rather than JSC's "non-numbers have low-bit set"
   trick, so the test cannot be folded into a single low-bit branch.
2. **Doubles.** JSC: subtract `DoubleEncodeOffset` after the cell test
   to recover the IEEE-754 bits. Lyng-js: no offset — finite doubles
   are stored *directly* as their IEEE bits
   ([value.rs:142-148](../../../crates/types/src/value.rs)),
   tested via "not the canonical-NaN-with-known-kind pattern". This is
   strictly *cheaper* for `untag_double!` (zero instructions) but
   strictly *more expensive* for `check_double!` (have to test for
   tagged-NaN exclusion).
3. **SMI payload.** JSC SMI payload is also the low 32 bits but the
   tag is in the high 16. Lyng-js SMI payload is the low 32 bits with
   tag in bits 32–47. `untag_smi!` on both is "truncate to w-register"
   = zero AArch64 instructions on a register-sized read; the mov-w
   handles the truncation implicitly.

These differences are why DSL-0 vocabulary is `check_smi!`,
`check_object_ref!`, `tag_object_ref!` (lyng terminology) rather
than `check_int32!`, `check_cell!`, `tag_cell!` (JSC terminology).
The shapes happen to coincide on some operations and diverge on
others — see the [delta table](#irreducible-deltas-vs-llint) below.

## SMI encoding

A 32-bit signed integer is packed by
([value.rs:137-139](../../../crates/types/src/value.rs)):

```rust
pub const fn from_smi(value: i32) -> Self {
    Self::tagged(TagKind::Smi, value.cast_unsigned())
}
```

i.e. the raw two's-complement bits go into the low 32 bits of the
`u64`, and the high 32 bits get `TAG_HEADER | (4 << 32) =
0x7ff8_0004_0000_0000`. Reading back
([value.rs:269-276](../../../crates/types/src/value.rs)):

```rust
pub const fn as_smi(self) -> Option<i32> {
    if self.is_smi() { Some(self.payload().cast_signed()) } else { None }
}
```

Untagging is a 32-bit read of the low half of the 64-bit slot. On
AArch64 with the `Value` already in `xN`, that compiles to a single
`mov wM, wN` (or — when loaded from memory — a `ldr wM, [..]`
read of the low half). No mask is needed; the W-register form of
the X-register already zeroes the upper 32 bits.

Round-trip is covered by [`smi_round_trip_and_numeric_helper_work`](../../../crates/types/src/value.rs)
([value.rs:413-423](../../../crates/types/src/value.rs)).

## Double encoding

For doubles ([value.rs:142-148](../../../crates/types/src/value.rs)):

- Finite values store `value.to_bits()` directly with no offset.
- NaN canonicalizes to `CANONICAL_NAN_BITS = 0x7ff8_0000_0000_0000`,
  which collides with the `TAG_HEADER` prefix *but* the kind field is
  zero — not in `1..=10` — so `is_tagged_bits` returns false and the
  value is treated as a double. The
  [`nan_is_canonicalized_without_colliding_with_tags`](../../../crates/types/src/value.rs)
  test ([value.rs:468-476](../../../crates/types/src/value.rs))
  pins this.
- The
  [`finite_doubles_with_tag_kind_bits_are_not_tagged`](../../../crates/types/src/value.rs)
  test ([value.rs:438-465](../../../crates/types/src/value.rs))
  walks all 10 tag-kind values placed at the kind shift and asserts
  each is a finite double that satisfies `is_double` and *no* tagged
  predicate. This is the safety property the DSL `check_double!` macro
  inherits.

`untag_double!` is zero instructions: the IEEE bits in `xN` already
*are* the double. `tag_double!` from `f64` is also zero instructions
(`fmov xN, dM`) for the finite case; the NaN-canonicalization branch
is a slow path.

The header-with-kind constant is a 48-bit immediate. On AArch64 it
materializes as two instructions (`mov` of the low half, `movk lsl

or an `or` against a memory operand.

## Per-operation asm sequences (AArch64)

The handler asm cited here is from the normalized baselines in
[reports/lyng/dsl-asm-baseline-aarch64/](./dsl-asm-baseline-aarch64/).
The DSL macros should produce code that, after inlining into a
handler, reduces to the sequences below. Where the baseline already
exhibits the pattern, the file and line are cited.

### `check_smi!(value, fail_label)`

Conceptually: AND with `TAG_HEADER`, compare to `TAG_HEADER`, branch
if not equal; then AND with `TAG_KIND_MASK`, compare to `4 << 32`,
branch if not equal.

In practice the compiler fuses both checks against a single composite
constant. From [`Add.asm:99-113`](./dsl-asm-baseline-aarch64/Add.asm)
where both `op_add` operands are checked for SMI:

```asm
    mov     x27, #17179869184              ; 0x4_0000_0000 — kind=4 in bits 32–47
    movk    x27, #32760, lsl #48           ; 0x7ff8 — TAG_HEADER prefix
    mov     x10, #281470681743360          ; 0xffff_0000_0000 — TAG_KIND_MASK
    movk    x10, #32760, lsl #48           ; mask high bits = TAG_HEADER too
    and     x11, x8, x10                   ; first operand: mask off payload
    and     x10, x9, x10                   ; second operand: same
    cmp     x10, x27                       ; equal to "tagged-SMI" pattern?
    ccmp    x11, x27, #0, eq               ; if first was equal, check second
    b.eq    L36                            ; both SMI → fast path
```

Single-operand `check_smi!` would drop the `ccmp` and stay at one
`and / cmp / b.ne` triple.

### `check_object_ref!(value, fail_label)`

Same shape as `check_smi!` but with the kind constant `5 << 32 =
0x5_0000_0000` instead of `4`. Conceptually:

```asm
    mov     xK, #0x5_0000_0000             ; kind=5 (ObjectRef)
    movk    xK, #0x7ff8, lsl #48           ; or with TAG_HEADER
    mov     xM, #0xffff_0000_0000          ; TAG_KIND_MASK
    movk    xM, #0x7ff8, lsl #48           ; ... composed with header
    and     xT, xVal, xM
    cmp     xT, xK
    b.ne    fail_label
```

Three instructions in the fast path (`and / cmp / b.ne`) after the
mask constants are hoisted, identical in shape to a JSC `check_cell!`.
The structural cost is the *same* as JSC; the literal mask values
differ. (See the delta table for why "same shape" only holds at the
predicate level, not at the slot-loading level.)

### `check_undefined!(value, fail_label)`

Same shape; kind constant is `1 << 32` and payload is 0, so the
fused constant is exactly `0x7ff8_0001_0000_0000`. Compiles to one
`cmp xVal, xK` plus `b.ne` (no AND needed because the payload must
be exactly zero too — the *entire* `Value` matches the constant).

### `check_null!(value, fail_label)`

Same as `check_undefined!` with constant `0x7ff8_0002_0000_0000`.

### `check_bool!(value, fail_label)`

Mask kind region with `TAG_KIND_MASK | TAG_HEADER`, compare to
`0x7ff8_0003_0000_0000`. Three instructions: `and / cmp / b.ne`.
The boolean *payload* (true vs false) is preserved in bit 0 of the
low word so an immediately-following `as_bool` is a single `tst xVal,
#1` against the same register.

### `check_double!(value, fail_label)`

Negation of `is_tagged_bits`. The compiler implements it as:

```asm
    mov     xM, #0xffff_0000_0000          ; TAG_KIND_MASK
    movk    xM, #0x7ff8, lsl #48           ; + TAG_HEADER
    and     xT, xVal, xM
    cmp     xT, xHdr                       ; xHdr = 0x7ff8_0000_0000_0000
    b.ne    is_double_label                ; high bits differ → not tagged → double
    ; else: validate kind in [1..=10] for the "tagged" path
```

The inverted form (jump to slow path when *not* a double) is what
arithmetic handlers emit. `op_add` materializes the kind validator
inline ([`Add.asm:51-56`](./dsl-asm-baseline-aarch64/Add.asm)):

```asm
    and     x9, x2, #0x7ffffffffffffffe    ; even-aligned upper bound
    cmp     x2, #4
    ccmp    x9, #4, #4, hs
    b.eq    L16
```

— this is the bounds check for "operand index in handler" rather
than a value-kind test, but it shows the `ccmp` idiom the compiler
reuses for chained predicates.

### `untag_smi!(value, dst)`

Zero work. `mov wDst, wSrc` if the value is in an X-register;
implicit zero-extension means the high bits are gone. When the value
is loaded from memory the corresponding sequence is `ldr wDst, [..]`,
which is exactly what `Move.asm` shows reading the operand index
([`Move.asm:30-34`](./dsl-asm-baseline-aarch64/Move.asm)):

```asm
    ldr     w12, [x0, #20]    ; pc-relative read of operand byte
    ldr     x13, [x0, #80]    ; register-file base
    add     w11, w12, w11     ; compute register index
    ldr     x13, [x13, #24]   ; deref to register storage
    ldr     x11, [x13, w11, uxtw #3]  ; load Value (full 64 bits)
```

The `Value` itself comes back as a full X-register read because the
high bits of the slot carry the tag — it's only on *successful*
`check_smi!` that the codegen knows to drop to the low W-register
read for arithmetic.

### `tag_smi!(int_reg, dst)`

`orr xDst, xHdrKind, xPayload` where `xHdrKind` is the precomputed
`TAG_HEADER | (4 << 32)` constant and `xPayload` is the W-reg
zero-extended into X. Two instructions if `xHdrKind` is hot in a
register; the compiler usually keeps it live across a basic block
once any SMI handler has materialized it.

### `untag_object_ref!(value, dst)`

`mov wDst, wSrc` — same as `untag_smi!`. The payload *is* the
`NonZeroU32` `ObjectRef` id, sitting in the low 32 bits.

### `tag_object_ref!(ref_reg, dst)`

`orr xDst, xHdrKind5, xRefId` — same shape as `tag_smi!` with
the kind-5 constant.

### `tag_undefined!(dst)`

Single `mov` + `movk` to materialize `0x7ff8_0001_0000_0000`. In
practice the codegen materializes the constant once per handler
prologue if it's referenced repeatedly and reuses the register.

### `tag_null!(dst)` / `tag_bool!(b, dst)` / `tag_sentinel!(s, dst)`

Identical shape — only the kind discriminator and (for booleans/
sentinels) the payload differ. Three or fewer instructions each.

## Irreducible deltas vs LLInt vocabulary

DSL-0 names its primitives after the *lyng* encoding rather than
the JSC LLInt encoding because the latter implies a cheaper
slot-loading sequence that the current Value layout *does not
provide*. The table below quantifies the deltas per operation. "Same
shape" means "same instruction count to within one immediate-load",
not "byte-identical asm".

| DSL operation                                            | LLInt instrs (JSC) | Lyng-js instrs | Reason                                                                                       |
| -------------------------------------------------------- | ------------------:| --------------:| -------------------------------------------------------------------------------------------- |
| `check_smi!` / `check_int32!`                            | 2 (AND + B)        | 3 (AND + CMP + B.NE) | JSC uses single-mask AND-test-zero on `NumberTag`; ours needs a kind-equality check.       |
| `untag_smi!` / `untag_int32!`                            | 0                  | 0              | Both: W-register read zero-extends.                                                          |
| `tag_smi!` / `tag_int32!`                                | 1 (ORR with `NumberTag`) | 1 (ORR with `xHdrKind4`) | Both: one OR against a register-resident constant.                                  |
| `check_double!`                                          | 1 (AND-test-nz)    | 3 (AND + CMP + B.NE) | JSC: bit 49 set ⇒ number. Ours: equality of high 16 bits to `TAG_HEADER`.                |
| `untag_double!`                                          | 1 (subtract offset)| 0              | Lyng-js wins here — no `DoubleEncodeOffset` to subtract.                                     |
| `check_cell!` / `check_object_ref!`                      | 2 (AND + CBZ)      | 3 (AND + CMP + B.NE) | Same predicate cost asymmetry as `check_smi!`. Single-operand fast path is still ≤4 cycles. |
| `untag_cell!` / `untag_object_ref!`                      | 0 (cell ptr is the value, modulo low bits) | 0 (W-register read) | Both zero work, but see `load_record_shape!` below. |
| `load_cell_shape!` / `load_record_shape!`                | 1 load (`ldr w, [cell, #structureID_offset]`) | **2 loads** (`ldr xRec, [heap_base, refId, lsl #3]` then `ldr wShape, [xRec, #shape_off]`) | **Side-table indirection.** `ObjectRef = u32` resolves through the object pool, then the `ObjectRecord` is dereferenced. Documented in [`jsc-aligned-engine-roadmap.md` §2](./jsc-aligned-engine-roadmap.md). |
| `load_inline_slot!(record, slot)` / `load_record_inline_slot!` | 1 load          | **2 loads**    | Same indirection: must reach the record first.                                              |
| `check_undefined!`                                       | 2 (CMP + B)        | 1 (CMP + B) — single 64-bit compare against pattern | Lyng-js wins here: undefined is one canonical 64-bit value, no AND needed.        |
| `check_null!`                                            | 2 (CMP + B)        | 1 (CMP + B)    | Same reason.                                                                                |
| `check_bool!`                                            | 2 (AND + CMP)      | 3 (AND + CMP + B.NE) | Roughly same.                                                                              |
| `tag_undefined!` / `tag_null!`                           | 1 (MOV imm)        | 2 (MOV + MOVK to materialize the 48-bit pattern) | Lyng-js patterns need a wider immediate.                                       |

### Reading the deltas

Per-handler hit-path total cost (rough, in instructions, fast path
only):

| Handler          | LLInt fast path | Lyng-js fast path | Delta | Dominant cause                                                |
| ---------------- | --------------: | -----------------:| ----: | ------------------------------------------------------------- |
| `Move`           | ~3              | ~4                | +1    | tag-load width                                                |
| `Add` (SMI/SMI)  | ~8              | ~10               | +2    | `check_smi!` per operand × 2                                  |
| `GetById` (mono) | ~7              | ~12               | +5    | **`load_record_shape!` double indirection** (the big one)     |
| `Increment`      | ~4              | ~5                | +1    | one `check_smi!`                                              |

The `GetById` row is the irreducible structural delta — eliminating
it requires moving from `ObjectRef = u32` + side table to
`*mut ObjectHeader` packed into the NaN-tag space, which is
roadmapped separately ([`jsc-aligned-engine-roadmap.md` §"Pointer-identity
cells"](./jsc-aligned-engine-roadmap.md)). DSL-0 accepts the
2-load record-shape sequence and exposes it as a single macro
(`load_record_shape!`) so the substrate can be reused after the
encoding refactor lands.

The smaller `check_smi! / check_double!` deltas (one extra `cmp`
per check) are arithmetic-loop hot but only matter for the SMI-fast
path; DSL-0 will track them as a separate evidence ticket and only
act if asm-diff shows them dominating after the indirection is
gone.

## Decision: DSL-0 substrate uses the current Value layout

DSL-0 generates code for the encoding documented above. The macro
vocabulary uses lyng-native names (`check_smi!`, `check_double!`,
`check_object_ref!`, `tag_object_ref!`, `load_record_shape!`,
`load_record_inline_slot!`) rather than JSC-imported names
(`check_int32!`, `check_cell!`, `load_cell_shape!`). This signals to
future readers that:

- the predicate shapes are different from JSC by design
  (NaN-tag-with-kind-field, not high-bit number tag), and
- the cell vocabulary is `object_ref` plus `record` to make the
  side-table indirection explicit at the macro layer.

Pointer-identity cells (folding `ObjectRef → ObjectRecord` into the
`Value` itself) is *not* part of DSL-0. It becomes a separate
evidence-driven refactor if the DSL-0/1 asm-diff baselines show
`load_record_shape!`'s extra load is the dominant remaining cost vs
JSC on `GetById`-heavy workloads. The DSL substrate is built to make
that future swap a localized change: only the `load_record_*!`
macros and their callers move; every `check_*!` and `tag_*!` macro
stays put because they operate on the `Value`-level tags, not on the
record-level pointer.
